# 在积木里造一块 RGB 点阵屏：从逐像素刷新到跑满 240Hz

如果不用图片、不用视频，只靠原生画笔积木，能不能在 Kitten N 里做一块支持 RGB 颜色的点阵屏？

这次，我用 **NekoC 将 TypeScript 编译成原生积木**，从最直接的像素绘制开始，逐步做出了一个可复用的点阵显示模块，并在普通 `.bcmkn` 项目中运行。

最终，经过优化的增量动画示例，在我的正常播放器环境里显示到了 **240.0 FPS**，跟上了显示器的刷新率。

不过，真正值得记录的，是它从“能画出来”到“跑得够快”的过程。

## 用画笔模拟一块屏幕

点阵屏的基本思路很简单：

把逻辑画面划分成网格，每个格子保存一个颜色，再把这个颜色画到舞台上的对应位置。

例如，使用 **32×20** 的逻辑分辨率，每个像素放大到 **28×28** 个舞台单位，就能得到：

```text
逻辑分辨率：32 × 20
像素放大倍数：28
显示区域：896 × 560
```

这样，一个只有 640 个逻辑像素的画面，就能覆盖舞台的大部分区域。

每个像素使用 RGB888 颜色：

```ts
rgb(255, 90, 40)
```

也就是红、绿、蓝三个通道各使用 8 位，能够表达约 1677 万种颜色。

整个显示过程使用原生画笔积木，由单个角色完成，编译后仍然是可以直接导入的 `.bcmkn` 文件。

## 第一关：画出了画面，却画不快

最直观的刷新方式是：

1. 遍历所有像素；
2. 读取像素颜色；
3. 设置画笔颜色；
4. 绘制对应格子；
5. 下一帧重新执行。

逻辑上没有问题，但积木运行器需要解释执行每一步操作。

一个像素看起来只是一个色块，背后却可能包含坐标换算、颜色转换、列表读取和多次画笔移动。乘上数百个像素后，每帧的开销就很可观了。

因此，优化的关键不是单纯“让循环更快”，而是：

> 尽量少计算、少换色、少移动，也少画那些根本没有发生变化的内容。

## 从整屏重画，改成只更新变化区域

对于通用画面，模块采用前后帧缓冲：

- 后缓冲保存准备显示的新画面；
- 前缓冲保存已经显示的画面；
- 两者比较，只绘制颜色变化的部分；
- 同一行连续且同色的变化像素，尽量合并处理。

而对于移动方块这样的简单动画，还能进一步优化。

假设一个方块向右移动一格，它的大部分区域其实没有变化。真正需要更新的只有：

- 左侧露出来的一条背景；
- 右侧新增的一条方块。

于是，原来需要擦除并重画整个方块的操作，就变成了两个窄矩形。

示例中的背景和彩条也只在初始化时绘制一次。每帧只处理方块边缘和底部移动光点，不再扫描整块屏幕。

这就是高速示例采用的**增量绘制**。

## 最意外的开销：常量也在反复计算

排查生成的积木时，我发现了另一类浪费。

一些结果早已确定的表达式，仍然被编译成多层运算积木，例如：

```ts
max(0, floor(0))
```

它的结果就是 `0`，但如果没有正确折叠，每次执行仍然要经过取整、绝对值和算术运算。

颜色计算也有类似问题：

```ts
rgb(8, 12, 24)
```

三个通道都是常量，完全可以在编译时计算出最终结果，而不必留给播放器处理。

修复后，TS 前端会在内联展开之后折叠支持的纯数字表达式：

```ts
max(0, floor(0))           // → 0
rgb(8, 12, 24)            // → 527384
setPenColor(rgb(8,12,24))  // → "#080c18"
```

动态变量、随机数和计时器等仍然保留运行时求值。

这一步减少的不只是运行开销，也让生成的积木明显变少。

## 固定颜色，直接使用原生颜色字段

动态 RGB 颜色需要转换为原生画笔支持的颜色属性，这会产生额外计算。

但对于背景色、方块颜色这样的固定颜色，没有必要每帧重新做 RGB→HSV 转换。

因此，高速路径直接把固定颜色编译成十六进制颜色字段：

```text
背景：#080c18
方块：#ff5a28
光点：#28dcff
```

动态 RGB 功能仍然保留；在高速示例中，只有初始化动态彩条时需要进行颜色转换。

## 画一个矩形，也有细节

用粗画笔画矩形，听起来只需要一条线。

实际测试却发现，原生画笔的圆形端点和圆角会留下覆盖缺口。在绘制时可能不明显，但用背景色擦除移动物体时，就会留下细小残影。

最终采用的方式是：

- 粗线覆盖中心；
- 内缩描边补齐边缘和角落；
- 再用更细的一圈完成覆盖。

我也尝试减少一圈描边，但官方播放器截图中出现了橙色点线和青色轨迹，说明擦除不完整。

所以，这部分最终保留了两圈补边。性能优化不能只看计数器，还要确认画面真的画对了。

## 共享绘制代码，减少积木体积

绘制函数如果在多个调用位置完整内联，生成的积木会快速膨胀。

后来，矩形绘制主体被放进一个共享的原生自制积木中，通过单角色共享坐标变量调用。

同时，还做了两项小改动：

- 列表使用原生 `all` 模式一次清空；
- 高速路径不再初始化用不到的两份帧缓冲列表。

这些优化叠加后，高速示例的积木数量从 **2616 个降到了 989 个**，减少约 **62%**。后来加入右下角 FPS 文字显示后，项目为 **1052 个积木**。

## FPS 不能用单帧时间差随便算

测试过程中，计时方式也踩了坑。

官方计时器约每 **50ms** 更新一次。如果直接计算：

```text
FPS = 1 ÷ 单帧耗时
```

就可能遇到连续两帧读到相同时间，或者读数只能跳到几个固定档位的问题。

最终改为在至少一秒的窗口内统计：

```text
平均 FPS = 完成帧数增量 ÷ 实际时间增量
```

右下角通过原生文字印章显示：

```text
FPS: 240.0
```

文字每个统计窗口刷新一次，先擦掉旧读数，再打印新读数，避免重叠。

## 最终效果：正常播放器跑到 240.0 FPS

优化后的示例保留了：

- 单角色原生画笔渲染；
- RGB 颜色支持；
- 32×20 逻辑像素网格；
- 896×560 舞台显示区域；
- 移动方块与光点动画；
- 右下角平均帧率显示。

在我的正常播放器环境中，这个示例能够达到 **240.0 FPS**，跟上显示器刷新率。

这里需要明确测试范围：这是**少量区域变化的增量动画**，并不意味着每帧任意改写全部 RGB 像素，也能达到同样的速度。

此外，示例原来的“15 / 30 / 60 档”实际按调度次数分频，并不是严格的墙钟限帧。在高刷新率环境里，全速档可以超过 60 FPS。

## 总结

这次点阵屏实验让我感受最深的是：

> 在积木运行器里，性能往往来自“少做多少事”，而不是“把同样的事情做快多少”。

从整屏刷新到增量更新，从运行时常量计算到编译期折叠，从重复换色到固定颜色字段，再到共享绘制主体，每一步都在减少不必要的工作。

最后得到的不只是一个能跑的动画，而是一套可以继续用于像素游戏、仪表盘、波形显示和简单软件渲染的原生画笔显示基础。
